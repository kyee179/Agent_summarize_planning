# Login, profiles and onboarding

This version adds hosted email/password accounts and a separate local workspace for each verified account. Supabase authenticates users; journals, calendar events, tasks and notes remain in SQLite on this computer. Cloud data synchronization is not implemented.

## 1. Understand the lifecycle

1. **Start locked.** The process checks its local API security token, opens the small account registry and renders the welcome screen. It does not open the original journal database. Continue offline explicitly opens the original local profile. An account opens only after the hosted service verifies its user identity.
2. **Verify identity.** The pinned `@supabase/supabase-js` 2.118.0 SDK sends email/password over HTTPS to the configured project. The backend calls `getUser` with the returned access token and requires a confirmed, authenticated user. The stable ownership key is the verified issuer plus user ID. Email and display name are labels, never ownership credentials. Request bodies cannot select an account's profile ID.
3. **Open one workspace.** `server/auth/registry.cjs` maps that identity to a random device profile ID. `server/auth/gateway.cjs` selects its database, integrations, credentials, telemetry and quota. New accounts start empty. The original database retains the reserved `local` identity and its existing Google connection.
4. **Finish onboarding.** Choose timezone, available hours, review time and local rules or a service using your own API key. Optional source permissions start off. An unchecked option can copy local journals, events, tasks and notes into an empty signed-in workspace. The source is read through a read-only SQLite snapshot. Connections, credentials, activity, embeddings and saved analyses are excluded. If the source uses an older schema, first open the local profile so its existing migration/backup flow can run.
5. **Work under a session.** The backend issues a random, opaque local capability. Electron keeps it in the main process; the renderer never receives hosted access or refresh tokens. Development browsers use an HttpOnly, SameSite=Strict session cookie through the trusted Vite proxy. The existing process token, exact loopback host and origin checks remain required.
6. **Close before switching.** Sign-out invalidates the capability, aborts the workflow, closes integrations/database handles, stops reminders and clears displayed workspace state. Guarded store methods and response checks reject delayed results from the old profile. The desktop and browser clients also discard delayed responses. The workspace React tree remounts for each identity/session transition.

`src/features/AuthGate.jsx` owns sign-in, signup, confirmation and recovery. `Onboarding.jsx` owns first-run preferences. `AccountPanel.jsx` owns export, switching and explicitly confirmed device-data removal. `electron/sessionBridge.cjs` keeps desktop session headers private and binds the Google consent handoff to the current workspace. `server/agent/cancellation.cjs` interrupts pending provider/tool work even if a transport ignores its abort signal; the gateway prevents late writes.

## 2. Configure Supabase afterward

The integration is ready without a real project. Until configured, email sign-in is disabled and Continue offline works. No account service was provisioned and no real signup/recovery messages were sent during implementation.

1. Create a Supabase project and enable email/password authentication. Keep email confirmation enabled. Set the project's minimum password length to at least 12 to match the application. Configure production email delivery and review the provider's email/rate limits before distributing the app.
2. In **Authentication → Email Templates**, include the `{{ .Token }}` code in **Confirm signup** and **Reset password** messages. The application accepts 6–10 digit codes. Confirmation links may be used externally followed by normal sign-in, but this version's in-app password recovery requires the code template; it does not process recovery deep links. Use a useful, trusted Site URL if your templates also include links.
3. Copy the **project URL** and **publishable app key**. The accepted URL is HTTPS under `*.supabase.co`; the accepted key starts with `sb_publishable_`. Legacy JWT anon keys, custom domains, self-hosted projects, secret keys and service-role keys are not supported by this initial configuration UI.
4. On the welcome screen choose **Set up account sign-in** and enter those public values. Alternatively configure server-only `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` in the ignored environment. Saved UI configuration takes precedence. These are separate from Google Calendar OAuth and AI service credentials.
5. Create a synthetic test account, confirm its email code, sign in, finish onboarding, sign out and sign back in. Test password recovery and remembered-session restoration with the actual project before release. These live checks remain pending.

The public configuration is saved locally in `hosted-auth.json`. No service-role key is needed: authentication, password updates and logout use user-scoped SDK requests. Do not put credentials into `VITE_` variables, source code, issues or commits.

Primary documentation: [password sign-in](https://supabase.com/docs/reference/javascript/auth-signinwithpassword), [server verification](https://supabase.com/docs/reference/javascript/auth-getuser), [email codes](https://supabase.com/docs/reference/javascript/auth-verifyotp), [email templates](https://supabase.com/docs/guides/auth/auth-email-templates), [API key types](https://supabase.com/docs/guides/getting-started/api-keys).

## 3. Session and data behavior

- Access tokens stay in backend memory. A local app session expires after 24 hours. The backend refreshes tokens within 60 seconds of expiry and rechecks the hosted user after five minutes without verification. Concurrent requests share a refresh. An unsuccessful verification closes the workspace; the local profile remains available offline.
- Keep me signed in stores only a refresh token, issuer and device profile ID in Electron's OS-encrypted `session.encrypted`. Startup refreshes and re-verifies its owner before opening data. It rejects a token/profile mismatch. Sign-out clears the remembered session immediately and attempts hosted revocation. Hosted JWTs follow the service's expiry/revocation behavior; remote logout is not a promise of instant JWT invalidation everywhere.
- No plaintext fallback exists for remembered sessions or new service keys. When secure OS storage is unavailable, sign-in works without remember-me and local rules work without keys. Linux's `basic_text` backend is rejected. See [Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage).
- Each profile has its own OS-encrypted AI/search/Google credentials, integration state, memory index, reminders and telemetry. Legacy environment settings belong only to the original local profile. Optional sources still require analysis-specific consent, and activity recording still requires a separate action.
- SQLite journal databases and portable exports are **not encrypted by this feature**. Local profiles trust the operating-system account. This is account separation inside the application, not protection against an administrator or someone reading the device's files. No cloud journal storage, multi-device sync, team sharing, social sign-in, MFA UI or hosted account-deletion UI is included.
- Account → Export workspace downloads journals, events, durable tasks/session links, notes and allowlisted preferences as JSON. Keep the personal export private. Copying local data is a one-time, explicit operation into an empty account workspace; it is not ongoing synchronization or an arbitrary JSON import endpoint.
- Account → Remove this workspace from this device requires typing the exact workspace name. It closes the workspace and removes only its selected UUID directory and registry entry. The hosted sign-in account and original local profile remain. Re-signing in creates a new empty device workspace. The reserved original local profile cannot be removed through this action.

## 4. Budgets and validation

Remote AI analysis has one in-flight request per workspace and a persistent default allowance of 10 attempts per UTC day. The settings API accepts a user limit from 1 to 100. The registry reserves an attempt before provider work begins, including requests that later fail or fall back; local rules use no remote allowance. These device-side controls do not replace hosted billing enforcement, service rate limits or cross-device abuse prevention. Account operations also have persistent per-address and per-device minute limits, separate from AI usage.

Validation uses synthetic accounts, journals and temporary directories. Backend tests cover cross-account journal/memory/task/apply/export boundaries; late login and analysis; actual SDK confirmation/recovery requests against a fake HTTPS transport; token refresh, restart and owner mismatch; encrypted storage; local-copy exclusions; device-removal containment; quotas; and cookie/origin security. Client tests cover IME-safe forms, cleared passwords, optional-copy consent, onboarding persistence and delayed-response rejection. Desktop smoke exercises locked startup, offline onboarding, per-profile secure setup, existing planning flows and sign-out. Browser smoke exercises the trusted proxy with the profile cookie.

Run `pnpm release:check`, `pnpm smoke:desktop`, `pnpm smoke:web` and the synthetic hosted desktop smoke `pnpm smoke:auth`. The real Supabase project's email delivery, policy, configured URL/key and live OS/provider refresh behavior must still be checked after configuration. Installer packaging and installed-app upgrade remain separate release work.

Final Windows verification in the implementation repository passed: **228 tests (47 frontend +181 server)**, quality policy, lint, offline evaluation, production build, offline Electron smoke, actual-SDK synthetic hosted Electron smoke and browser-cookie smoke. The strengthened local-copy check also passed: imported tasks belong to the new account, preserve their scheduled sessions and are not planned twice. Screens at 1280, 640 and 390 pixels were checked without horizontal overflow. No real hosted project, real account email or installed package was tested. GitHub CI is prepared to run both desktop flows; no new remote CI result is claimed for this local feature.
