# Fix — working GLM calls and simpler optional connections

## 1. Diagnose before switching the model

On 2026-10-15, the existing `glm-4-flash` key and official endpoint returned HTTP 200 for a short chat (~0.7 seconds) and a small native tool call (~1.2 seconds). The failure was reproducible in the application protocol: generating a full canonical proposal took about 20–30 seconds, sometimes returned JSON in ordinary content instead of `tool_calls`, and invented deadlines or omitted required estimate metadata. Repair turns then exhausted the 30-second request / 60-second workflow limits.

The fixed workflow still uses **glm-4-flash**, native official API calls and the existing budgets. `server/agent/compactProposal.cjs` declares a smaller wire schema: summary/references and up to eight tasks, each with title, evidence references, an importance level, an uncertain effort interval or null, and an assumption. The workflow expands this into the canonical contract. IDs and estimate links are generated locally; deadlines remain unknown, importance is inferred, confidence is low, and scope defaults to a next session. These are explicit conservative policies, not verified facts or measured durations. No calendar allocations are generated by the model.

For a single supplied journal the workflow constructs explicitly partial weekly context from the selected-journal summary/references. With multiple supplied journals, the model still supplies contextual summary/references. All expanded records pass the original canonical and semantic validators and deterministic scheduler. Bad references, ranges, dependencies, additional fields and invented deadline fields fail validation. The compact GLM protocol does not yet express verified deadline facts; confirmed fact ingestion remains future work.

`server/agent/tools.cjs` offers the valid next tool phase to GLM: read all supplied evidence, inspect planning context, optionally retrieve/research, preview, finish. Other adapters retain their existing schemas. Execution still checks permissions and state regardless of which tool was advertised.

`server/agent/glmToolText.cjs` accepts only a whole JSON tool envelope such as `{"name":"read_evidence","parameters":{"offset":0,"limit":20}}`, optionally enclosed in one JSON code fence. It rejects surrounding prose, extra keys and batches. The adapter converts that envelope into one ordinary tool call with a generated ID; it then goes through the same validators, budgets, preview and finish checks. A JSON-shaped instruction cannot grant access to an undeclared tool, write a calendar event or finish without a valid preview.

The repository preserves prompt 1.1.0 and pins policy **1.2.0**. Skill versions remain 1.1.0. The reviewed release manifest records the new policy hash. Existing user-added JSDoc comments are preserved.

### Exact GLM execution path

1. **Provider stays the same.** The effective configuration remains `AI_PROVIDER=glm`, `GLM_MODEL=glm-4-flash`, and the official BigModel endpoint. The credential stays in the ignored environment file. A successful small tool probe distinguished working authentication from failures in the larger application request.
2. **Reduce the wire contract.** `compactProposal.cjs` asks GLM for judgments it must make. For example, a task contains `title`, `evidenceIds`, `importance`, `effortMinutes: [15, 30, 60]` (or null), and `assumption`. It no longer has to generate IDs, estimate links, every canonical metadata field, or calendar slots. `expandProposal()` creates the canonical records, labels model estimates low confidence, sets unknown deadlines to null, and then invokes the existing validation path. An inverted effort range is rejected.
3. **Offer tools by phase.** `tools.cjs` exposes `read_evidence` until all initial evidence is read, then `get_planning_context`, then `preview_plan` and any explicitly authorized retrieval tools. A successful latest preview unlocks `finish_analysis`. `runtime.cjs` passes this list to the GLM adapter on each turn. The executor also enforces its state and permission checks.
4. **Normalize the observed alternate format.** `providers.cjs` first handles native `tool_calls`. Only when a stopped GLM message has no native call does `glmToolText.cjs` try a whole JSON envelope: `{"name":"read_evidence","parameters":{"offset":0,"limit":20}}`. The alternative `arguments` object and one exact JSON fence are supported. Prose, unknown envelope keys, arrays and bare proposals are rejected. A normalized call still consumes the ordinary tool and error budgets.
5. **Keep weekly context honest.** With one initial journal, the server derives an explicitly partial weekly summary from that entry. With multiple initial journals, GLM must supply the weekly fields and source references. This avoids asking it to invent a week from a single entry.
6. **Version the behavior.** Policy `1.2.0` describes this compact protocol; the release manifest pins its hash. Existing prompts and skill versions are preserved, so rollback can restore the preceding code/prompt pair.

The accepted path is `read_evidence → get_planning_context → preview_plan → finish_analysis`, with bounded optional retrieval before finalization. Native and normalized JSON calls use the same validator and deterministic scheduler. Limits remain 12 model turns, 16 tool calls, 3 validation errors, 30 seconds per provider request and 60 seconds per workflow. The fix does not hide timeouts behind local fallback: the live gate requires remote completion.

### Regression checks

`tests/glm-compact.test.cjs` verifies strict envelopes, conservative expansion, invalid ranges/references, permission checks and a complete mocked workflow. `tests/agent-workflow.test.cjs` covers the native GLM request/response path and prompt version. The opt-in `pnpm eval:live` runs three synthetic journals against the real configured provider. It fails when any case uses fallback. Public CI uses deterministic offline tests and needs no provider key.

### Live result

The final three-case live run completed remotely in **9.7, 11.3 and 14.5 seconds**, with no fallback. All live gates passed. Provider-reported usage for those runs was 31,409 input and 514 output tokens; monetary cost is unknown in the report. These are three synthetic regression examples, not an independent model-quality benchmark.

Metrics now identify version **2.0.0**: articles/possessive pronouns and simple verb inflections are normalized while retaining content-word order; task matching rejects a negation mismatch. “Update CV” matches “update my CV”; “Delete my CV” and “Do not update CV” do not. Dataset labels and thresholds are unchanged. Reports across different metric versions require recomputation before comparison. See `evaluation/README.md` for limits and human-review requirements.

## 2. One Google button for customers

The connection card has **Connect Google Calendar**, **Refresh Google Calendar**, and **Turn off Google Calendar**. Connect expresses read-only consent, starts the existing state/PKCE loopback flow, opens the system browser through a dedicated trusted Electron IPC handler, polls for completion, then automatically synchronizes the user's actual primary calendar. It reserves today plus the next seven local dates, including scheduling buffers, using the app's timezone. The separate advanced controls still allow selection of other calendars and custom ranges. Google events remain read-only.

The backend retains the original scope verification, encrypted token vault, refresh/cancel/replay protection, bounded pagination and atomic busy-cache replacement. Quick sync locates the `primary` flag returned by Google, rather than assuming the first calendar is primary. The cache still expires after 30 minutes; **Refresh Google Calendar** updates it before planning. Apply keeps source/calendar freshness checks.

Google requires a one-time **app-owner setup** before any customer can log in. In Google Cloud, enable Calendar API, configure the consent screen, add the testing account while the app is in testing, and create an OAuth client of type **Desktop app**. Configure the ignored local values `GOOGLE_CLIENT_ID`, optional issued `GOOGLE_CLIENT_SECRET`, and the existing local encryption key. `pnpm setup:env` generates a missing local encryption key. Restart the app after configuration. Customers of a properly configured distribution press Connect and consent; they do not each need to create a Google Cloud project. Public distribution still requires an appropriate consent/verification and configuration-delivery plan.

Official reference: [Google desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app).

## 3. Activity without a separate ActivityWatch installation

On Windows, **Enable desktop activity** starts a bundled helper, `server/integrations/windows-activity.ps1`. `server/integrations/desktopActivity.cjs` launches the fixed helper with a hidden window only after explicit consent. The helper uses standard Windows foreground-process and idle-time APIs. It reads **app process names and idle time only**, with no window titles, full URLs, screenshots, clipboard contents or keystrokes.

The sampler runs every five seconds, excludes idle periods of at least 60 seconds and clock/suspend gaps, and saves immutable approximate intervals of up to one minute in the existing activity store. Different endpoint samples are not credited as continuous app usage. Data retains the existing 30-day expiry, source invalidation and per-analysis permission checks. Tracking stops on pause, deletion or app shutdown; a new app session requires enabling it again. Enabling collection does not itself authorize sending observations to the AI provider.

The packaging configuration unpacks the PowerShell helper from Electron's archive so the OS can execute it. Linux/macOS show this built-in option as unavailable and retain the existing ActivityWatch path. Corporate PowerShell restrictions may require local administrator assistance; the application does not change machine policy.

ActivityWatch remains an advanced import option for historical observations and browser domains. A browser watcher extension needs its local ActivityWatch server and cannot replace all desktop watchers. An extension installed inside Electron would not observe another Chrome/Edge application's tabs. The built-in app-name sampler avoids a separate ActivityWatch download on Windows, while browser-domain detail still requires a separately authorized browser integration. It cannot reconstruct activity from before tracking was enabled.

References: [ActivityWatch architecture](https://docs.activitywatch.net/en/latest/architecture.html), [official browser watcher](https://github.com/ActivityWatch/aw-watcher-web).

## 4. Tavily search and explicit controls

`server/integrations/research.cjs` supports Tavily at the fixed `https://api.tavily.com/search` endpoint. The key is passed in the authorization header. Requests explicitly use basic depth, three results, no generated answer, no raw page content/images, and `auto_parameters: false`. Both direct and agent searches retain consent, concurrency, rate, timeout, byte and two-search workflow limits. Returned source links/snippets remain unverified, low-confidence evidence with no confirmed task facts. Provider relevance scores cannot become factual confidence. Reported credit usage is shown when available.

Tavily is selected when its key exists (or no search key exists); an existing Brave-only configuration remains compatible. Set `WEB_SEARCH_PROVIDER=tavily` explicitly to select it. The connection card and analysis source controls include an on/off web-research switch; manual search has separate consent. No search runs merely because a key is configured.

The app owner needs a Tavily account/API key. Put `TAVILY_API_KEY` only in the ignored local `.env`, then restart. A distributed app must use an appropriate private search service or per-user key setup; embedding a shared secret in a public Electron package would expose it. Credentials, OAuth tokens, activity records and live reports stay out of Git.

References: [Tavily Search API](https://docs.tavily.com/documentation/api-reference/endpoint/search), [Tavily account](https://app.tavily.com/).

## Google consent follow-up: access eligibility and token exchange

Two separate failures were observed in the live setup:

1. **Google returned 403 before callback.** The project was External / Testing with zero test users. After explicit user approval, the signing-in account was added to the test-user list and the saved count became one. A fresh request reached Google's test-app notice. This was an app-owner configuration correction; credentials and account identifiers remain private.
2. **The connection ended during the callback.** The callback consumed the one-use state, set the pending listener record to null and began the asynchronous token exchange. Status briefly reported no pending authorization while the outcome still said waiting. Both UI polling and the temporary live harness could mistake that transitional state for a finished flow; the harness then cancelled the in-flight exchange. A synthetic delayed exchange reproduced this gap.

The corrected backend tracks an exchange separately from the unconsumed state. Public status keeps `pending: true` with `lastOAuth: exchanging` until the token response is checked and stored, or fails/cancels. The callback listener stays open until that response finishes; repeated state is rejected without issuing a second token request. Connect and sync refuse overlapping exchanges. Cancellation advances the existing generation counter, so late tokens cannot save or clear a newer authorization.

The UI shows Connecting during pending authorization and stops polling only for explicit terminal outcomes. The private live harness follows the same rule. This prevents a temporary lack of a listener record from being treated as disconnection. State validation, PKCE, the two read-only scopes, token encryption, fixed endpoints and the bounded token request remain enforced.

Regression coverage in `tests/integrations.test.cjs` holds the token response open while checking pending status, replay rejection, parallel-operation rejection and successful completion. The cancellation test also starts a new authorization before the old response arrives. The UI regression in `IntegrationSettings.test.jsx` verifies that polling survives an interim exchange response and synchronizes only after completion. Real Google token-endpoint reachability was separately confirmed with an unauthenticated diagnostic request (HTTP 400, no credentials sent). Local release verification passed: 148 tests (21 frontend and 127 server), quality policy, lint, offline evaluation, production build and the real Electron smoke using a temporary synthetic database. Real user consent, token exchange and primary-calendar sync subsequently passed in the desktop app. Hosted Windows/Linux CI passed for callback fix a568554 (run 38732943685). See the completed matrix below.

## GLM retrieval follow-up: advertise the journal citation boundary

The ordinary live plan completed in 21.3 seconds with memory/web permission enabled, but the model chose no optional searches. That was a valid core plan, not proof of retrieval execution. A test-only adapter then selected the authorized memory and Tavily paths explicitly. Searches succeeded, but initial proposal turns exceeded the 30-second request budget. A reduced-output diagnostic exposed a second failure: retrieved source IDs appeared in `summaryEvidenceIds`, which is reserved for the selected journal. Validation correctly rejected them and repair consumed more time. Removing duplicate web snippets did not resolve the failure, so that experimental projection was not adopted.

`server/agent/compactProposal.cjs` now describes the journal-only summary boundary in the tool schema and enumerates its allowed journal evidence IDs. With no selected-journal evidence, that list must be empty. The summary schema is copied independently so its enum cannot constrain task citations or contextual summaries. Task citations still accept authorized memory/web evidence. Canonical validators, source storage, scheduler, permissions, full research responses, and time/output limits are preserved. No summary text is silently rewritten to make a bad citation pass.

The regression rejects a related-journal ID in the selected summary, then accepts that ID as task evidence and validates the completed contract. It also checks empty evidence. After this correction, the full live path completed twice in 31.1 and 30.5 seconds: `read_evidence → get_planning_context → search_personal_memory → research_web → preview_plan → finish_analysis`. Both had one actual SQLite lexical memory hit, one Tavily request/credit, three low-confidence citations, valid contracts and no fallback. These cases show integration execution, without establishing general latency or tool-selection quality.
